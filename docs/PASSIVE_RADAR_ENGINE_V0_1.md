# Passive Radar Engine v0.1

## Смысл этапа

`Passive Radar Engine v0.1` — следующий ключевой этап после стабилизации текущего билда.

Главная цель: приложение должно не ждать, пока человек вручную откроет экран и введёт напоминание, а само пассивно проверять разрешённые источники данных и вовремя напоминать о важном.

Ручной ввод остаётся дополнительной возможностью, но не центром продукта.

## Главный сценарий

```text
Пользователь живёт обычной жизнью
→ в календаре появляется событие
→ Радар сам видит событие
→ создаёт или обновляет RadarCard
→ не плодит дубли
→ выбирает подходящее время напоминания
→ показывает уведомление
→ может объяснить, почему напомнил
```

## Минимальный источник для v0.1

Первый пассивный источник:

```text
Android Calendar Provider
```

Почему календарь первый:

- это уже структурированные данные;
- там есть даты и время;
- Android даёт официальный способ чтения через разрешение владельца;
- это хорошо подходит для проверки идеи пассивного радара.

## Базовый поток

```text
CalendarSourceReader
→ CalendarSourceEvent
→ SourceFingerprint
→ Capture / normalized source text
→ Analysis
→ RadarCard
→ NotificationSchedule
```

## Требования к v0.1

### 1. Фоновая проверка

Радар должен периодически проверять календарь настолько, насколько это разрешает Android.

Для первого рабочего варианта допустимо:

- запуск проверки при старте приложения;
- ручная кнопка повторного сканирования;
- подготовка архитектуры под WorkManager;
- последующее добавление настоящей периодической фоновой проверки.

### 2. Защита от дублей

Повторное сканирование календаря не должно создавать одинаковые карточки бесконечно.

Для каждого события нужен стабильный ключ:

```text
calendar:<calendarId>:<eventId>:<beginMillis>
```

Если карточка с таким ключом уже есть, Радар должен обновить её или пропустить, а не создавать дубль.

### 3. Окна контроля

Для ближайших событий контроль должен быть сильнее, для дальних — спокойнее.

Базовая схема:

```text
0–6 дней     → ACTIVE
7–13 дней    → MEDIUM
14–20 дней   → WEAK
21+ дней     → BACKGROUND
```

### 4. Своевременное уведомление

Карточка должна не просто существовать в списке, а приводить к действию:

```text
важное событие скоро
→ уведомление появляется заранее
```

Для первого варианта достаточно простого правила:

- событие сегодня → напомнить как можно скорее;
- событие завтра → напомнить заранее;
- событие через несколько дней → создать карточку и держать в радаре.

### 5. Объяснение whyText

Каждая карточка должна объяснять причину:

```text
Почему Радар это показал?
Потому что в календаре есть событие через N дней.
```

### 6. Прозрачность и разрешения

Радар не должен читать данные скрыто.

Обязательные условия:

- владелец выдаёт разрешение READ_CALENDAR;
- если разрешения нет, календарный источник не работает;
- на экране должно быть понятно, что именно читает Радар;
- Google Tasks/Задачи пока не считаются частью календарного источника.

## Что не входит в v0.1

Пока не делаем:

- скрытую прослушку;
- чтение всех приложений подряд;
- облачный обязательный анализ;
- сложную ML-модель;
- автоматическое чтение сообщений;
- агрессивные уведомления без объяснения.

## Критерий успеха

Этап можно считать успешным, когда выполняется сценарий:

```text
1. Пользователь добавил тестовое событие в календарь.
2. Приложение получило разрешение READ_CALENDAR.
3. Радар нашёл событие.
4. Радар создал RadarCard.
5. Повторное сканирование не создало дубль.
6. Карточка содержит понятный whyText.
7. Уведомление появляется в подходящий момент.
```

## Следующий технический порядок

1. Стабилизировать текущий билд после календарных изменений.
2. Проверить APK на телефоне.
3. Добавить/проверить стабильный sourceKey для календарных событий.
4. Добавить защиту от дублей в repository/controller layer.
5. Подготовить NotificationSchedule для календарных карточек.
6. После ручной проверки — подключить WorkManager для фонового периодического сканирования.
