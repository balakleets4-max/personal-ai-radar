# Quality and Product Principles

Этот документ фиксирует обязательные правила разработки `Личного ИИ-Радара`.

## Главная цель продукта

`Личный ИИ-Радар` должен быть реально полезным пассивным помощником, а не приложением, которое отнимает время.

Главный смысл:

```text
Человек живёт своей жизнью,
а Радар тихо помогает ему не упустить важное.
```

Приложение должно:

- пассивно работать с разрешёнными владельцем источниками данных;
- своевременно напоминать о важном;
- снижать когнитивную нагрузку;
- не требовать постоянного ручного ввода;
- не превращаться в игру, ленту, соцсеть или приложение для бесконечного сидения;
- открываться только тогда, когда владельцу реально нужно посмотреть детали, настроить источник или вручную добавить захват.

## Запрет на заплатки и костыли

Категорически запрещено строить приложение из заплаток и костылей.

Исключение допускается только для экстренных ситуаций:

```text
критический билд упал
→ нужно срочно вернуть сборку в рабочее состояние
→ временное решение явно помечается
→ после стабилизации заменяется нормальной архитектурной правкой
```

Во всех обычных случаях решение должно быть качественным сразу.

## Что считается плохой правкой

Плохая правка:

- чинит только видимый симптом;
- ломает архитектуру;
- создаёт технический долг без крайней необходимости;
- прячет проблему вместо решения;
- добавляет новую функцию поверх шаткого фундамента;
- заставляет пользователя делать лишнюю ручную работу;
- превращает пассивный Радар в обычный блокнот или todo-лист;
- загрязняет интерфейс техническими деталями;
- создаёт дубли, шум или лишние уведомления.

## Как надо делать работу

Перед изменением кода нужно:

1. Понять продуктовую цель.
2. Проверить текущую архитектуру.
3. Найти правильный слой для решения.
4. Оценить побочные эффекты.
5. Делать маленький, но качественный блок.
6. Проверять сборку и поведение.
7. Давать понятный чек-лист ручного теста.

## Правило для источников данных

Каждый источник должен подключаться как самостоятельный источник, а не маскироваться под ручной ввод.

Пример:

```text
CalendarSourceEvent
→ sourceKey
→ source-specific import/use-case
→ RadarCard
```

Неправильно:

```text
CalendarSourceEvent
→ длинная строка текста
→ обычный ручной parser
→ Мысль
```

## Правило для интерфейса

Обычный пользовательский интерфейс должен показывать:

- что важно;
- когда важно;
- почему Радар напомнил;
- что можно сделать.

Он не должен без необходимости показывать:

- внутренние ключи;
- email источника;
- parserVersion;
- analyzerVersion;
- служебные данные;
- длинные технические объяснения.

Технические данные допустимы только в отдельном debug-режиме.

## Правило для уведомлений

Уведомления должны быть своевременными и полезными.

Они не должны быть шумом.

Каждое уведомление должно отвечать на вопрос:

```text
Почему это важно сейчас?
```

## Главный критерий качества

Если функция не помогает человеку меньше забывать и меньше тратить внимание, её нельзя считать полезной для Радара.

Радар должен экономить время владельца, а не забирать его.
